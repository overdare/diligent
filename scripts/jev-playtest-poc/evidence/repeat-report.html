Why the previous loop was slow

The previous loop serially performed three PIE status checks and three observations per action. Windows-local fresh TCP connection took about 0.3–1 ms; status, a narrow observation, and an unknown-method error all waited about 112 ms. Persistent connections and moving Studio to foreground did not remove that delay. Inserting 50 ms of idle reduced the following response wait to about 62 ms. This identifies a periodic Studio-side request-processing wait as the leading explanation; its exact C++ polling/tick implementation was not available for confirmation.

The optimized observer runs continuously on its own channel while choice and input execute. The status supervisor polls once per second; dispatch uses the newest cached observation and explicit PIE/client identity. A stale, changed or illegal choice is discarded. The measured outer observation cadence improved from 903 ms to about 113 ms.

What changed enough to play effectively

  • The baseline camera center hit the Baseplate, so firing consumed ammo without core damage. The adapter now reads the actual CoreHitbox and player camera, uses the supported look input, then verifies alignment and boss damage.
  • Blind Q rolls pushed the character into hazards. The adapter now proposes destinations outside observed hazard geometry and directional rolls only when their endpoints clear that geometry.
  • The model previously reopened the current equipment menu 29 times. Current-page no-ops are removed; a prepared roster advances to deployment.
  • Repeated aim toggles are replaced by desired aim-on/aim-off transitions tied to combat phase.
  • Short bounded shot bursts reduce repeated input RPC overhead. Live server Feedback hit flags and accepted state changes support outcome checks.

Failure lessons retained

  • Unit tests missed a duplicate Trace.write kind argument; the first live run failed before input. A dispatch-path regression now covers it.
  • The original semantic and HUD-only combat trials both ended in WIPE; semantic boss damage was zero. Connectivity and legal actions alone did not establish useful play.
  • The optimized run still ended with only 37 player HP: spatial safety and timing need broader seed/pattern tests.
  • Periodic request waiting remains in the shipping Studio binary. A server-side event-driven receiver or reduced poll interval is the next engine investigation; a transport rewrite alone is not supported by these measurements.

Reusable PoC contracts

Game adapter: observation params → state → useful legal candidates → balanced input events → revalidation → effect facts. Chooser: choose(goal,state,actions) → action ID, diagnostics, latency. Swap adapters with --adapter and model integrations with --chooser-factory; the runtime retains authority over Studio I/O and outcome verification. See README.txt for commands.

Evidence and evaluation limits

  • One trial is not a win-rate estimate.
  • Prepared spatial candidates and runtime scheduling changed together.
  • Only Ollaya/Laya was called; remote Jev was not exercised.
  • Feedback logs are actual server events, but not a complete raw engine console log.

Use matched-seed rule/random/Laya/Jev trials with the same candidate generator to estimate model contribution. The single winning run demonstrates an executable integrated harness.
