Native Diligent / OVERDARE playtest integration
=============================================
Date: 2026-10-02 KST

Result
------
The requested path was exercised against the real Windows Studio, through a
Mac dev-cross Diligent agent: read the installed game-specific harness, modify
its Luau source, save and validate it, start a new game, select useful actions
with native Laya, observe actual effects, and stop the same game session.

The last episode reached the accepted server VICTORY state with boss HP 0 and
player HP 125. A separate Studio readback confirmed PIE running=false and the
maintained source hash. No business game scripts, health, damage, or win rules
were changed by the native maintenance tools. The source diff changes only
movement expectations and position rounding in the harness.

Architecture implemented
------------------------
1. Diligent is the author/maintainer. It can inspect project Lua and GUI, write a
   game-specific adapter, install/read/update its Studio source, validate it,
   run an episode, inspect the trace, and revise the adapter between episodes.
2. The adapter persists as editable Studio code in
   ReplicatedStorage.DiligentPlaytestHarnesses.<name>. It owns accepted facts,
   useful candidate calculations, balanced input batches, actual game feedback,
   effect expectations, and truthful terminal rules. A common LocalScript driver
   publishes bounded JSON frames. These assets remain saved for later runs.
3. The native TypeScript runner owns the repeated observation/choice/input loop,
   freshness and validity checks, cancellation, local traces, and session cleanup.
   It contains no Hollow Warden names, combat geometry, controls, or terminal rules.
4. Laya chooses among the adapter's currently useful candidates. Singleton choices
   are deterministic. Laya does not inspect arbitrary Lua or generate game code
   on every frame; Diligent prepares/maintains that code outside the timed episode.

Tools are registered on the existing Studio provider. Web and TUI consume the
existing tool protocol; MCP exposes the same tools and final results. No new
client-specific autoplay implementation or Python production dependency was added.

Lessons from failures and delays
-------------------------------
- Rich state should come from accepted server snapshots/feedback and actual
  geometry/GUI visibility. Hidden authored HUD defaults are not authoritative.
  The driver heartbeat proves adapter liveness; a game-specific adapter must
  also account for the freshness of its own snapshot source.
- Studio RPC latency is not primarily TCP connection setup in the measured local
  probes. Windows localhost narrow observe waited about 112 ms with sub-ms
  connection setup; persistent connections and foregrounding did not remove it.
  A 50 ms idle gap reduced the next read wait to about 62 ms. A Studio polling or
  scheduling cadence is a plausible explanation, not a proved C++ root cause.
- The native observer initially added an unnecessary 100 ms after every RPC.
  Changing it to a minimum start-to-start interval removed that extra wait.
  Observation continues while the model or input runs; there is no serial
  observe -> model -> input -> observe blind interval.
- A chooser result must be checked against the latest candidate frame immediately
  before input. One fire_core choice was discarded after phase/validity changed
  in the maintained run. Candidate geometry is an estimate; subsequent state and
  server feedback establish the effect.
- Completed input is not proof of success. Effects retain observed before/after
  values. No effect, runtime error, input cancellation, timeout, and game defeat
  are separate outcomes. Cleanup uses an independent signal and does not stop a
  replacement or pre-existing session.
- Luau JSONEncode exposes arrays as numeric-key objects in this Studio build.
  Only protocol array fields are normalized, in numeric order. Arbitrary state
  objects remain objects. Exactly 16 actions are supported; an off-by-one check
  was found and repaired.
- Source installation must preserve exact bytes. Long-bracket literals dropped
  an initial newline in a real Editor probe. Quoted literals now preserve LF,
  CRLF, quotes, backslashes, delimiter-like text, and Unicode; five read-only
  Editor roundtrips passed. Updates also compare the previous Source inside the
  Editor transaction, not only before it. A successful edit is never replayed
  merely because save or validation subsequently fails.
- The user's mounted /Volumes/overdare-newgame was unavailable. Dev-cross ran
  with repository cwd and live RPC editing/saving. The general map rollback
  baseline could not be captured without the mounted map; this test preserved
  harness source versions explicitly. It does not prove full-map rollback.
- The stored default coding model chatgpt/gpt-5.6-luna was not recognized by the
  current Diligent catalog. The test selected advertised gpt-6-luna/max for its
  thread without changing the global configuration. The first invalid describe
  call included an extra name; Diligent corrected it and continued.
- The maintenance/gameplay turn exceeded the client's aggregate five-minute
  limit during final log-analysis/report thinking. The game had already won and
  stopped. That attempt remains recorded as turn_timeout, pass=false. A report-only
  continuation in the SAME thread completed in about 24 s. Its acceptance scope
  explicitly includes prior persisted tool results. It did not replay the edit
  or game. Separate preparation/report deadlines from timed gameplay deadlines.

What is and is not established
-----------------------------
The game-specific-code maintenance loop is feasible and implemented, and the
requested real Diligent start/play/stop path is verified. XState or a reactive
state library can be used inside a game's adapter but is not a prerequisite.
They do not themselves discover useful actions or trustworthy game outcomes.

Automatic first-time adaptation to arbitrary UGC, automatic discovery of all
observation bindings, guaranteed improvement across code revisions, matched-seed
quality evaluation, a raw Unreal/Lua console-log stream, and remote Jev account
authentication/latency/billing were not established. This implementation reads
the adapter's real game feedback live, not the full raw Studio console.

For reliable autonomous improvement across many UGC projects, the next acceptance
layer should retain source revisions with their episode hashes, define meaningful
per-game goals/coverage metrics, compare repeated runs under matched conditions,
and restore a known version after regression. The existing source-hash update and
trace contracts provide the execution boundary for that work. One successful
adapter or one improved run cannot serve as a universal quality guarantee.
