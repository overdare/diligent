# Performance
OVERDARE streams everything to players during play, so each distinct asset and mesh adds load.
- Whenever you place 10 or more similar Parts or MeshParts, you must consider merging them into a single MeshPart inside a ProceduralModel (the `geometry-recipe` skill), and state what you decided. Keep them in separate MeshParts only when they need different materials or must move or behave independently.
- Objects that look the same should share one `ovdrassetid`, whether they come from the Asset Store or a ProceduralModel: place copies of one and vary properties such as Size, Color, and Material, rather than creating a separate asset for each placement. For 100 floor tiles that each disappear on their own, bake one tile and clone it 100 times; a floor that never splits apart is better merged as above. Never bake the same tile 100 times: that creates 100 separate assets for players to stream.
- Prefer **Static** Mobility for level geometry that never moves (buildings, terrain, rocks, trees, background props): it uses precomputed lighting and costs far less to render. Reserve **Movable** for objects that move, animate, or that players interact with; too many Movable objects in one scene degrades performance.
  - Mobility can be set only on direct children of Workspace (in Luau, `obj.Mobility = Enum.MobilityMode.Static` or `Enum.MobilityMode.Movable`), and everything under them inherits it, so plan the top-level grouping while building. During play a Static object rejects position changes and unanchoring, so anything that must move goes under its own Movable top-level object, never inside a Static one.

# Editor World Editing
- Use `studiorpc_instance_upsert` only for simple, fixed changes to a few instances. Use `studiorpc_execute_luau` (`target: "Editor"`) for any Editor operation that needs procedural logic: loops, conditions, computed positions or arrangements, or steps that build on earlier reads. Check unfamiliar classes and properties with `studiorpc_instance_schema_search` before writing that code.
- Decide when the behavior must run: once as an Editor command, persistently as Studio-managed behavior, or during gameplay. Do not silently substitute gameplay behavior for Editor behavior.
- Parent a new instance under workspace before setting top-level-only properties such as Mobility. To get its GUID, return its name and resolve it with `studiorpc_level_browse`; GetDebugId and PivotTo are not available in the Editor VM.

# Adding 3D Assets
Choose per object; a typical scene mixes all three. Whichever you use, keep one art style across the scene: match the proportions, palette, materials, and level of detail of what is already there, and pass that style to any sub-agent that builds props.
- **Asset Store**: check it first; a fitting asset is the fastest. Find assets with `overdaresearch` (`source: "assets"`) and import them with `studiorpc_asset_drawer_import`, or `studiorpc_asset_drawer_import_bulk` for several. Prefer assets that share one concept and keep reusing that set; the `asset-pack-import` skill handles themed packs.
- **ProceduralModel**: when no asset fits and the object needs a modelled shape — props, furniture, vehicles, decorations; expect this for most custom props. Delegate new props to one `general` sub-agent (it edits the level): tell it to load the `geometry-recipe` skill, pass each prop's goal, any known size and parent, and the scene's art style, and ask for each model's GUID, recipe path, and warnings. Use the skill yourself to edit an existing model. Its MeshParts are regenerated from the recipe, so change the recipe, not the parts.
- **Parts**: when primitive shapes are the object itself — walls, floors, platforms, blockouts, and collision volumes. Never stack Parts to imitate a modelled object; that is what ProceduralModel is for.

# Visual Effects
Effects carry much of how a game feels. Choose in this order:
- **VFXRecipe**: the default for custom effects. A Niagara-based effect that layers source items in Base/Detail/Extra, usually adapted from an official template, and exposes some parameters for runtime tuning via SetParam/SetParamAt.
- **VFXPreset**: a ready-made effect such as fire, explosions, barriers, or healing, used as-is when one fits and its internals need no changes.
- **Beam / Trail / ParticleEmitter**: part-based effects with limited expressiveness; use them only for what the two above do not cover.

# Game UI
- Players are on mobile, in landscape, with touch only. Use the `gui-builder` skill to create, review, or restyle GUI; it covers layout, system controls, contrast, ZIndex, and fonts.
- Write in-game text in plain English unless the user asks for localization, whatever language the conversation is in. Do not use emoji or special Unicode symbols (e.g. ⭐, →); they do not render consistently across devices.

# Writing Gameplay Scripts
- Write and change script source with `studiorpc_script_add` and `studiorpc_script_edit`.
- NEVER use file-level tools (edit, write, bash, apply_patch, etc.) to directly manipulate `.lua` / `.luau` files. Script source lives inside the `.ovdrjm` level file, not as standalone files on disk.
- Use explicit Luau type annotations where practical.
- Every script write through `studiorpc_script_add` or `studiorpc_script_edit` returns a Luau validation report: `OK` per clean script, `E`/`W` per diagnostic, then `SUMMARY`. Judge the write by `SUMMARY errors`, not by the call succeeding.

<roblox-compatibility>
OVERDARE largely follows Roblox's engine model and Luau API, so Roblox knowledge usually works. The known exceptions are listed here. When an API behaves unexpectedly or you are unsure it exists, check `overdaresearch` or `studiorpc_instance_schema_search`; if it is unsupported, tell the user the specific limitation before choosing an alternative.

# Units and Assets
- 1 unit = 1 cm, so 1 Roblox stud (≈ 28 cm) is 28 units.
- Asset paths use `ovdrassetid://[number]`.

# Transforms in a Hierarchy
- Child Parts follow later changes to their parent Part's position, rotation, and scale, even when Anchored; no Weld is needed, and resizing a parent also scales its children's Size.
- Position, Orientation, and CFrame stay world space for reads and writes, as in Roblox, in gameplay scripts and Editor Luau. Convert parent-relative offsets to world space before assigning them.
- New MeshParts default to `Anchored = true`. Set `Anchored = false` only for parts that need physics; unanchoring a part just to make it follow its parent instead lets it fall.

# Cylinder Parts
Cylinders are oriented along the Y axis (Roblox uses X), with Size `(Diameter, Height, Diameter)`.
| Object | Size | Orientation | Notes |
|--------|------|-------------|-------|
| Coin / Disc (flat) | `(100, 5, 100)` | `(0, 0, 0)` | Already flat; just use a small Height |
| Log / Pipe (sideways) | `(50, 200, 50)` | `(0, 0, 90)` | Rotate 90° around Z to lay along X |
| Wheel (rolling) | `(80, 20, 80)` | `(0, 0, 90)` | Thin cylinder on its side, like a log |

# Characters
- Humanoids use a single capsule collision by default, so part-based hit detection (e.g. a headshot via Touched on Head) does not work until you enable the HitboxType option.
- Do not move a character by repeatedly writing HumanoidRootPart `Position`/`CFrame` (via `Heartbeat`, `while`, etc.); it fights Unreal's CharacterMovementComponent and causes jitter or teleporting. Drive movement through the character's movement system.
- Do not use HumanoidRootPart.Anchored to freeze a character; the property is accepted but is not a reliable way to stop it.

# Collision
OVERDARE uses Collision Profiles instead of Collision Groups. Each object's profile sets its response per channel as Block, Overlap, or Ignore, and a pair's result depends on both sides: they block only if both Block, overlap if either side Overlaps, and ignore each other if either side Ignores.

# Scripting
- After `Destroy()`, a reference is not `nil` (`obj == nil` stays false) and reading its properties raises an error; check it with the global `isnil(obj)`.
- In a LocalScript, `PlayerAdded` and `CharacterAdded` fire for every player, including the local player and players who joined earlier; filter explicitly when you need others only.
- These do not exist in gameplay scripts; `studiorpc_instance_schema_search` cannot confirm that something is absent:
  - `Debris`: use `task.delay(seconds, function() obj:Destroy() end)`
  - `warn()`: use `print`
  - `DateTime`: use `os.time()` for Unix seconds; it does not replace every DateTime feature
- The Editor VM (`studiorpc_execute_luau`) has no `task`, `os`, or `isnil`; these replacements apply to gameplay scripts only.
</roblox-compatibility>

<overdare-built-in-features>
OVERDARE has built-in features for common game mechanics. Use them instead of building equivalents by hand, and check `overdaresearch` for their exact usage.

- **CanClimb**: BasePart property that makes a surface climbable on contact, subject to a slope-angle condition
- **Character movement**: Humanoid properties for acceleration, friction, rotation speed, deceleration, air control, and multi-jump (`MaxJumpCount`)
- **Ragdoll**: `Humanoid:ChangeState(Enum.HumanoidStateType.Ragdoll)` enables physics ragdoll with no rigging or constraints
- **CameraOffset**: a Camera property (not Humanoid) that offsets the camera in Custom and Scriptable modes, e.g. for camera shake
- **TPS Strafing System**: built-in view-locked strafing with 8-direction animation, enabled from a LocalScript (e.g. `RotationType = CameraRelative`)
- **Outline / Fill**: object emphasis instances; Highlight does not exist. Parent one under its target or set `Adornee`. Outline has Color and Thickness; Fill has Color, Transparency, and DepthMode (`Enum.FillDepthModeType`); both have Enabled.
- **BlendSpace**: blends multiple animations by parameter
- **ActionSequence**: timeline editor combining animation, sound, camera, VFX, events, and hit detection for combos, dashes, and chained skills
- **SimulationBall**: plays back precomputed ball trajectories consistently across clients, queryable by time (e.g. `GetCFrameAtTime`)
</overdare-built-in-features>
