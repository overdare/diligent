- **ActionSequencer**: Timeline-based visual editor for combo attacks, dashes, chained skills — integrates animation, sound, camera, VFX, and markers in one UI

# Clear Separation Between Server (Script) and Client (LocalScript)

Unlike Roblox, OVERDARE strictly separates server-side and client-side functionality.
- **Server functionality:** Must be written in `Script`
- **Client functionality:** Must be written in `LocalScript`
- **Example:** GUI and Camera related operations must run in a `LocalScript`

# Position / Size Units
- **Roblox:** 1 = 1 Stud (≈ 28 cm)
- **OVERDARE:** 1 = 1 cm (therefore 1 Stud equals 28 units in OVERDARE)

# Asset Path
- Asset paths must use the format `ovdrassetid://[number]`

# Parent-Child Hierarchy and Anchoring
- Child Parts **automatically follow the parent's position/rotation/scale changes** — no Roblox `Weld` needed (like Unity's parent-child relationship). This holds **even if the child is Anchored**.
- Child Parts use **Local Coordinates** relative to the Parent Part (opposite of Roblox, where child parts use independent World Coordinates).
- New Mesh Parts default to `Anchored = true` (opposite of Roblox). Set `Anchored = false` only when you actually want physics simulation on that part.
- Do NOT unanchor a part just to make it follow its parent — anchored children already follow the parent's transform. Unanchoring instead enables physics, so a part with nothing under it will fall through the floor.

# Mobility (Static vs Movable)
- Prefer **Static** for level geometry that never moves (buildings, terrain, rocks, trees, background props): it uses precomputed lighting and costs far less to render. Reserve **Movable** for objects that move, animate, or that players interact with — too many Movable objects in one scene degrades performance.
- Mobility is settable **only on top-level Workspace objects** (direct children of Workspace) and **cascades to their entire subtree** — a Static top-level forces every descendant Static, and Static objects cannot be moved, unanchored, or created at runtime. Split the hierarchy with this in mind: anything that must move at runtime belongs under its own Movable top-level object, not nested inside a static structure.

# CFrame
- All CFrame values are in **World Space** — there is no local CFrame concept
- When placing or offsetting objects in a parent-child hierarchy, always compute positions in **world coordinates**
- Do NOT use parent-relative offsets for CFrame; always convert to absolute world space first

# Spatial References
- Interpret ambiguous spatial directions and locations in the user's current viewport unless the user explicitly names world axes or absolute coordinates.

# Cylinder(Parts Shape)
- Unlike Roblox (X axis), a cylinder shape is oriented along the **Y axis**. 
- Size format: `(Diameter, Height, Diameter)`.
  | Object | Size | Orientation | Notes |
  |--------|------|-------------|-------|
  | Coin / Disc (flat) | `(100, 5, 100)` | `(0, 0, 0)` | Already flat — just use small Height |
  | Log / Pipe (sideways) | `(50, 200, 50)` | `(0, 0, 90)` | Rotate 90° around Z to lay along X axis |
  | Wheel (rolling) | `(80, 20, 80)` | `(0, 0, 90)` | Thin cylinder on its side, like log |

# Character and Humanoid
- Humanoids use a **single capsule-shaped collision** by default — per-body-part hitboxes are disabled. Roblox-style part-based hit detection (e.g. "headshot = 2x damage" via Touched on Head) will NOT work as-is; enable the **HitboxType option** first when per-part hit detection is needed.
- Do NOT move a character by looping over its HumanoidRootPart — periodically writing HumanoidRootPart `Position`/`CFrame` (via `Heartbeat`, `while`, etc.) fights Unreal's CharacterMovementComponent and causes jitter/teleporting. Drive movement through the character's movement system, not per-frame position writes.
- **HumanoidRootPart** cannot be `Anchored`, and its `Transparency` accepts only `0` or `1` (no partial transparency).
- **Humanoid Jump state**: the `Jumping` state persists for the whole jump animation and only becomes `Freefall` after it ends (in Roblox it flips to Freefall immediately). Don't rely on Roblox's jump→freefall timing.

# Collision Profiles
- OVERDARE uses **Collision Profiles**, not Roblox Collision Groups. Objects share a channel, and each object's profile sets its collision per channel independently and one-directionally as **Block / Overlap / Ignore** — so two objects on the same channel can behave differently. Don't model this as one bidirectional group per behavior the way Roblox does.

# Procedural Modeling
- Procedural modeling describes a form through generation rules and parameters. The rules define relationships between its parts; changing an input reruns those rules to produce the corresponding form. Parameters can represent dimensions, object counts or fill, spacing, or layout. This supports related variations and repeatable edits without manually repositioning each generated part.
- In Studio, `ProceduralModel` stores the generation Source, Size, and parameter attributes. Its MeshPart children are derived output. Change the rules or inputs for lasting changes; direct edits to generated children may be overwritten by regeneration. A parameter affects geometry only if the source actually uses it. Keep deliberate randomness controlled by a seed when reproducibility matters.
- Editor Luau configures the instance through the same editing API: create and parent it, set Source and inputs, and enable AutoRebuild. Studio owns automatic regeneration after the Editor command's VM has ended. A one-time script that creates ordinary parts does not by itself retain an editable generator. Regeneration is asynchronous; read the generated result in a later call. Do not call unsupported Rebuild/Bake methods or equate a successful assignment with a completed bake.
- Native Source uses Unreal Python (`import unreal`, `unreal.OvdrGeometry`, `ovdr_parts`), not Blender (`bpy`). Declare parameter defaults in `OVDR_PARAMETERS`, implement `on_generate(model, size, attributes)`, and declare generated parts with `model.part`. Geometry generation belongs inside that function. Use a working source example or authoritative documentation for function signatures; report a missing reference instead of inventing an unrelated runtime.

## Native Source authoring reference
The following is a complete minimal source module, adapted from the existing Studio geometry implementation. It creates repeated beveled segments as one material group. Adapt the generation rules to the requested form; this example is not a required object or layout.

```python
import unreal
import ovdr_parts as parts

G = unreal.OvdrGeometry
OVDR_PARAMETERS = {"segments": 3, "gap_cm": 2.0}

def check(ok, operation):
    if not ok:
        raise RuntimeError(operation + ": " + G.get_last_error())

def on_generate(model, size, attributes):
    width, depth, height = map(float, size)
    if min(width, depth, height) <= 0:
        raise ValueError("Generation extents must be positive")
    count = max(1, min(16, int(attributes.get("segments", 3))))
    gap = max(0.0, min(width / (2 * count), float(attributes.get("gap_cm", 2.0))))
    segment_width = (width - gap * (count - 1)) / count
    mesh = G.new_mesh()
    for index in range(count):
        piece = parts.chamfered_box(segment_width, depth, height, chamfer=0.6, origin_base=True)
        check(G.recompute_normals(piece, per_face=True), "normals")
        x = -width / 2 + segment_width / 2 + index * (segment_width + gap)
        check(G.append_mesh(mesh, piece, G.place(x=x)), "append")
        G.dispose_mesh(piece)
    check(G.set_uvs_from_box_projection(mesh, G.place(), unreal.Vector(100, 100, 100), 1), "UVs")
    model.part("Surface", mesh, "Plank", unreal.LinearColor(r=0.5, g=0.3, b=0.12, a=1.0), tile_cm=100.0)
```

- Editor Size.Y is the vertical extent; `Vector3.new(x_extent, height, z_extent)` is not `(width, depth, height)`. Native geometry uses centimetres with Z up. In the tested Studio mapping, the Source `size` tuple is `(Editor Size.Z, Editor Size.X, Editor Size.Y)`, so its native `(width, depth, height)` uses different horizontal axes. Name the space when writing dimensions and convert at this boundary. A native width=160, depth=45, height=240 corresponds to Editor Size `(45,240,160)` before model rotation. Check a non-cubic result's axes and proportions; rotation cannot repair geometry generated with the wrong dimensions.
- Validate input ranges and their combinations before emitting meshes: derived dimensions must remain positive after subtracting framing, gaps, or repeated layers. Check usable space and clearances, not only the outer box. Test a parameter's boundary cases as well as its default; individually valid values can form an impossible combination.
- Build geometry inside `on_generate`; module scope holds imports, constants, parameter declarations, and helper definitions. `G.*` operations can return False instead of raising, so check their results. `parts.chamfered_box(length, width, height, chamfer, origin_base)` creates a mesh; `G.place(x, y, z, pitch, yaw, roll)` provides its transform.
- Merge geometry that shares a material and tint with `G.append_mesh`, then call `model.part` once per material group. Dispose temporary mesh handles as you merge. Use explicit `unreal.LinearColor` for normalized tint values, and apply UV projection with a material tile size in the supported 25–400 cm range. Do not turn every repeated element into a separate MeshPart.
- Use exact, supported native preset names; do not invent a preset from an appearance adjective. The reference's `Plank` is a known working preset, not a naming pattern. Instance material value hints help identify valid names, but do not imply every string is accepted by model.part. If a native generation error names a preset, change that preset based on evidence rather than replacing unrelated valid materials.
- Through Editor Luau, create and parent the ProceduralModel, enable AutoRebuild, assign the complete Python module to Source, set Size, and initialize the declared parameters with SetAttribute. Subsequent edits update the same instance's Source, Size, or attributes; no gameplay Script or Play session is needed. Keep the model identity and reuse its Source for iteration.
- For a parameter test, use SetAttribute after the initial command has finished, then wait for the asynchronous result and inspect it without resubmitting Source. Restore the parameter after testing. A screenshot must actually be viewed, not merely created; a path or success flag is not visual evidence. If a remote screenshot path cannot be read, resolve its mounted project counterpart if available, otherwise report that the image could not be inspected. onScreen and projected bounds establish framing, not visibility through other geometry or visual correctness.
- This supplied contract and example establish the native authoring path even if documentation search returns unrelated results. Search for additional functions when needed; absence of a search match is not evidence that the documented mechanism is unavailable and does not justify changing Editor behavior to a gameplay builder.

# UX/UI Considerations
- Always consider mobile environment, NOT PC environment, when designing UI layouts — the screen is **landscape (horizontal)** orientation
- No keyboard input: Do not design interactions based on keyboard input. All player actions must be triggered through on-screen touch buttons
- Ensure sufficient contrast between text and background. If the background is complex or has large brightness variations, use overlays or panels to maintain readability for text.
- Top Left (Menu), Bottom Left (Joystick), Bottom Right (Jump Button) are system-default HUD elements shared across all UGC games — **NEVER** place, overlay, or wrap custom UI on top of them.
- Use ZIndex in 100-point bands so the runtime can validate the right things together. Put UI that should be checked against normal HUD conflicts in the same ZIndex band. Runtime overlap checks compare elements inside the same band.
  - 0-99: normal HUD/gameplay UI
  - 100-199: intentional overlays such as loading screens, modal dimmers, tutorial blockers
  - 200+: debug/special layers
- Do NOT use Emoji or Unicode special characters (e.g., ⭐, →) in game UI text. OVERDARE's rendering engine may not support them consistently across devices. Use plain text or image assets instead.
- Write all UI text in **English only**, unless the user explicitly wants localization (L10n). Do not default to the user's conversation language for in-game text. Keep it simple and plain — short, common words that are easy for a global audience to understand.
- OVERDARE's built-in UI system is minimal. If the user wants a visually rich UI, build it from external image assets: `ImageLabel` / `ImageButton`. Do this visual polish at the **end** of the project, not early — start with simple placeholder UI while building gameplay, and replace it with image assets as a finishing step if the user isn't satisfied with it.

- **Functions:** `local function GetScore(id: number): number`

# Explicit Dependencies
When a script `require()`s other modules, declare those dependencies clearly at the top of the file (e.g., in a comment block). Keep dependencies one-way and avoid circular requires.
- List every required module in a "Dependencies" comment.
- Prefer one-way dependency graphs.
- Do not create circular references (A requires B, B requires A).

```lua
-- PlayerController.lua
-- Dependencies:
--   - PlayerModel
--   - GameConfig

local PlayerModel = require(path.PlayerModel)
local GameConfig = require(path.GameConfig)
```
