# Persistent Goal Mode Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Follow the repository limit of one subagent per task. Steps use checkbox syntax for tracking. This document is a plan, not authorization to begin implementation.

**Goal:** Let a user explicitly activate a persistent session goal that Diligent continues across outer runs, with shared Web/TUI controls, observable limits, reliable cancellation, and resume.

**Architecture:** A runtime-owned `GoalController` coordinates the existing app-server execution path. A per-session append-only goal ledger persists state independently of the conversation tree. Model tools report completion/blockers; automatic admission, limits, and user interruption remain deterministic runtime responsibilities.

**Tech Stack:** Existing Bun, strict TypeScript, Zod, JSONL, JSON-RPC, React Web client, and TUI; no new dependency or database.

**Spec:** [Research and proposed design](../specs/2026-09-22-goal-mode-research-and-design.md). Read its proposed product choices and accounting limitations before execution.

## Global Constraints

- English only in all files.
- One runtime and protocol implementation for Web and TUI.
- Root sessions only; children participate in accounting and cancellation, not independent goal continuation.
- Goal mode never changes permission policy, selected model, or collaboration mode.
- Plan mode cannot auto-start execution; switching an active goal to plan mode pauses it.
- Use `Options` for runtime arguments such as `signal`; reserve `Config` for configuration values.
- Tests belong in package-level `test/`; public JSON-RPC scenarios belong in `packages/e2e/app-server/`.
- Preserve `onStop` as a result-ignoring lifecycle callback and core hooks as synchronous.
- Keep provider-token accounting distinct from invoice accounting; current compaction and unreported failed-call spend are not covered.
- Implement the six-state lifecycle, optional token cap, and proposed configurable 20-outer-run default described in the spec. Test configured behavior with synthetic values, not a snapshot of that default.
- Keep existing untracked files intact. If implementation creates a branch, use the repository's `feat/...` convention.

## Delivery order and shared interfaces

Tasks 1 through 6 form one releasable MVP; Task 7 verifies it and documents the contract.
Do not expose an enabled goal command before cancellation and accounting tests pass.

New schemas are exported by `@diligent/protocol` from `src/goals.ts`. Store-only fields
belong in runtime. The public snapshot is deliberately separate from execution handles:

```ts
type GoalStatus = "active" | "paused" | "blocked" | "budget_limited" | "usage_limited" | "complete";
interface ThreadGoal {
  id: string;
  threadId: string;
  revision: number; // Control revision, not incremented for every usage sample.
  objective: string;
  status: GoalStatus;
  tokenBudget?: number;
  maxTurns: number;
  turnsUsed: number; // Goal-attributed outer runs, not provider rounds.
  tokensUsed: number;
  cacheReadTokens: number;
  activeTimeMs: number;
  accountingScope: "reported_agent_tokens";
  reason?: string;
  completionEvidence?: string;
  createdAt: number;
  updatedAt: number;
}
type GoalChange =
  | { action: "set"; objective: string; tokenBudget?: number; maxTurns?: number; expectedRevision?: number }
  | { action: "edit"; objective: string; tokenBudget?: number; maxTurns?: number; expectedGoalId: string; expectedRevision: number }
  | { action: "pause" | "resume" | "clear"; expectedGoalId: string; expectedRevision: number };
interface GoalRunIdentity {
  goalId: string;
  epoch: number;
  outerRunId: string;
}
interface GoalUsageSample {
  identity: GoalRunIdentity;
  sessionId: string;
  coreTurnId: string;
  inputTokens: number;
  outputTokens: number;
  cacheReadTokens: number;
  cacheWriteTokens: number;
}
type SessionRunOutcome =
  | { status: "completed" }
  | { status: "interrupted" }
  | { status: "failed"; error: import("@diligent/core/agent").SerializableError };
```

`revision` plus the current goal ID rejects stale user controls. Runtime retains an
execution epoch separately; pause, clear, resume, edit and replacement invalidate old
admission callbacks. In-flight samples retain their original identity and are never
charged to a replacement goal.

`set` without an expected revision is allowed only when no goal exists. Replacing a
complete goal requires its current revision; unfinished goals reject replacement until
the user clears them. Control revisions are monotonic for the ledger across replacement.

RPC requests:

```text
thread/goal/get    { threadId }                         -> { goal: ThreadGoal | null }
thread/goal/set    { threadId, ...GoalChange }           -> { goal: ThreadGoal | null }
thread/goal/updated { threadId, sequence, goal }         -> notification; null means cleared
```

The tagged mutation deliberately avoids encoding every action as an arbitrary status
assignment. Notification `sequence` is monotonic across clears/replacements so clients
can reject stale delivery. Add optional `goal` to `thread/read` and an optional `goals`
capability defaulting to false when absent. Protocol version remains 1.

## Out of scope for this MVP

An independent evaluator, deterministic acceptance commands, automatic quota-reset
wakeups, daemon/cloud scheduling, time-budget enforcement, goal inheritance on forks,
and unrestricted autonomous goals on child sessions are separate changes. A later
evaluator must use provider-scoped ModelRef, be cancellable, account its own usage,
and treat inconclusive/error results as non-success.

## Approved follow-up: default availability and natural-language creation (2026-09-23)

This supersedes the original opt-in flag and user-command-only creation proposals.
Goal support is enabled unless `goals.enabled` is explicitly false. Both clients
reuse the existing goal protocol and status UI; no client-side intent detection
is introduced.

1. Add root-only, plan-disallowed `create_goal` with shared objective validation
   and optional safe positive token/run limits. Its description permits explicit
   persistent user requests only; ordinary tasks and untrusted quoted content do
   not authorize creation. The main model selects the tool without another model.
2. Buffer one creation in the originating ordinary user turn. Return `pending`,
   then persist through the existing idle goal controller after successful model
   execution and session writes. The source turn and its children remain outside
   goal accounting; charging starts with the first automatic goal run.
3. Reject duplicate/existing goals and child/internal/plan/disabled contexts.
   Revoke pending creation on user interruption/admission/steering, goal controls,
   mode/config changes, disconnect, and shutdown. Failure must not start a goal.
4. Cover propagation, persistence, accounting, default availability, cancellation,
   and tool isolation with deterministic tests. These tests do not establish the
   model's accuracy at interpreting natural-language intent.
5. Verify the shared backend, Web/TUI suites, typecheck, and lint. Update the user
   guide and OVDR-15262; retain the current branch and leave push/PR to the user.
