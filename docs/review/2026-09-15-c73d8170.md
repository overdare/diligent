## Findings

### F-01 — Studio RPC turn state is shared across concurrent threads

**Disposition**: Act now
**Lens**: Ownership | Operational correctness
**Confidence**: High
**Evidence**: The product host constructs one Studio RPC bundled provider for the server (`apps/overdare-ai-agent/sidecar/src/server.ts:163-183`; `apps/overdare-ai-agent/sidecar/src/tools/index.ts:19-30`). That provider allocates one `TurnSnapshotState` and every prompt hook, agent loop hook, and tool closure reads or mutates it (`apps/overdare-ai-agent/sidecar/src/tools/studiorpc/index.ts:44-60`, `62-128`, `198-252`, `282-307`). Each `onUserPromptSubmit` overwrites `sessionId`, `taken`, prompt metadata, and the human-edit capture. The app server's concurrency guard is per `ThreadRuntime`, not process-wide, so distinct threads can reserve and execute turns concurrently (`packages/runtime/src/app-server/turn-handlers.ts:68-84`; `packages/runtime/src/app-server/server.ts:586-673`). The new Edit.Log consumer also re-reads every `.consuming` file when a later turn starts (`apps/overdare-ai-agent/sidecar/src/tools/studiorpc/tools/edit-log.ts:248-273`), while each thread's loop hook takes whichever capture is currently in the shared object. Existing tests exercise one provider turn at a time and contain no interleaved two-thread case. Current TypeScript tests could not be rerun because Bun is unavailable in this review environment; the ownership collision is directly determined by the current closures and per-thread server lifecycle.
**Impact and mechanism**: If thread A starts and thread B starts before A's prompt loop or first map edit, B replaces A's state. A can then receive B's human-edit cache, or both turns can report the same rotated Edit.Log batch as edits preceding their own turn. More seriously, A's first mutating tool can create its rollback snapshot under B's session ID and prompt label; once either turn sets the shared `taken` flag, the other turn can edit without its own baseline. A later rollback can therefore offer a mislabeled or older world snapshot precisely when concurrent conversations are editing the same Studio project.
**Smallest responsible action**: Make Studio turn state session/thread-owned instead of provider-owned. Give each assembled main agent's Studio tools and loop hook access to the same state for that session, and have `onUserPromptSubmit` update only that session's state. If the bundled-provider context needs a lazy session-ID accessor to connect hook and tool assembly, add that bounded runtime context rather than serializing all threads or adding a second Studio RPC provider model.
**Scope and non-goals**: Cover rollback baseline metadata/once-per-turn state and human-edit capture/finalization. Preserve the existing project-wide Studio write lock, Edit.Log rotate-and-retry behavior, child-agent exclusion, v1/v2 tool behavior, and concurrent read-only conversations. Do not redesign snapshots, EditLogging, app-server thread concurrency, or the bundled-provider system beyond the context needed to bind state to a session.
**Verification**: Add an interleaved two-thread regression using one provider instance and one project: start A, start B, then run each prompt loop and first mutating tool. Prove each thread receives only its own turn-start human-edit capture, each creates one rollback baseline under its own session/transcript/prompt metadata, and neither thread's `taken` or capture-error state suppresses the other. Preserve crash-leftover replay and single-turn snapshot tests. Run the focused Studio RPC tests plus an app-server scenario with simultaneous turns on distinct thread IDs.
**Why now**: Commit `b4ef4d51` added Edit.Log capture to the already shared rollback state, expanding the consequence from snapshot labeling to creator-edit attribution and deletion. The same range also hardened per-thread interruption and replacement, making concurrent thread execution an actively supported lifecycle rather than a hypothetical future mode. Additional turn-scoped Studio features would inherit the same unsafe owner.
**Delivery**: Created issue #459 — https://github.com/overdare/diligent/issues/459
