## Findings

### F-01 — Background code-mode mutations are not durably recorded without a later cell collection

**Disposition**: Act now
**Lens**: Contract | Operational correctness
**Confidence**: High
**Evidence**: A scoped driver now remains attached after yielding, and `drive()` immediately takes and clears a result snapshot (`packages/runtime/src/tools/code-mode/session.ts:128-159`, `197-209`). Later nested completions emit live events and append records only to the cell's in-memory `nestedCalls` (`session.ts:320-342`). `TurnStager` deliberately ignores nested `tool_end` events because their parent result is expected to carry them (`packages/runtime/src/session/turn-stager.ts:49-63`). History reconstruction reads only records carried by a persisted `exec`/`exec_wait` result (`packages/runtime/src/app-server/thread-read-builder.ts:243-250`). Run closure waits for work but does not publish another durable snapshot (`packages/core/src/agent/loop.ts:249-256`, `281-284`).

A temporary diagnostic used the real app-server factory and public JSON-RPC test client. Its deterministic provider requested `exec` with `yield_control(); await tools.bash(...)`, waited for the nested completion notification, then ended the turn without `exec_wait`. The real nested command changed a temporary file. After completion, `thread/read` omitted the nested call, and the session JSONL contained no nested call ID:

```json
{"marker":"after","liveNestedEnds":[{"id":"review-exec#1","isError":false}],"historyToolIds":["review-exec","review-exec"],"nestedIdPersisted":false}
```

The existing background-dispatch e2e explicitly collects the cell through `exec_wait`, so it does not cover this missing-carrier path. The diagnostic's provider is an input, not evidence about real-model choices; the evidence is the runtime-owned mutation, live notification, and missing durable record.

**Impact and mechanism**: Reloaded or resumed transcripts can omit an operation that actually changed the project. The cell record remains only in process memory until a later collection; process restart loses it. Correct durable history therefore depends on an optional future model tool call rather than completion of the real operation. Web and TUI both consume the affected shared history. This finding concerns operation history, not a claim that arbitrary nested output should automatically enter provider context.
**Smallest responsible action**: Persist completed nested-call records through a runtime-owned path independent of a future `exec_wait`. Preserve the original parent ID and ensure later cell collection does not duplicate already-recorded calls. Retain compatibility with existing sessions whose nested records are embedded in parent result metadata.
**Scope and non-goals**: Cover background completion, interrupted-turn finalization, history reconstruction, and deduplication. Do not turn nested calls into unpaired provider-facing tool-result messages, force the model to wait, remove background execution, redesign code-mode permissions, or combine this work with worker-owner disposal (#511).
**Verification**: Add a public JSON-RPC e2e that yields, performs a real temporary-file mutation, completes the run without collecting the cell, and asserts the completed nested operation appears exactly once in `thread/read` both before and after a fresh server resumes the session. Also verify a subsequent `exec_wait` does not duplicate it, failure/interruption preserves completed operations, and existing metadata-only history remains readable. Run focused code-mode, session-staging, and thread-read tests.
**Why now**: `a9e11a01` enables nested calls after the driving result has already been persisted. The earlier carrier assumption no longer covers supported execution, and every additional background mutation can create another incomplete audit trail.
**Delivery**: Created issue [#556](https://github.com/overdare/diligent/issues/556) — `fix(runtime): persist background code-mode calls without cell collection`.

### F-02 — Luau-test cleanup adopts an unverified current PIE session and stops it

**Disposition**: Act now
**Lens**: Ownership | Operational correctness
**Confidence**: High
**Evidence**: `runOwnedTestSession` marks startup accepted after `game.play`, but records a session ID only during subsequent polling (`apps/overdare-ai-agent/sidecar/src/tools/studiorpc/tools/luau-test/session.ts:103-119`). A polling failure goes directly to cleanup (`session.ts:140-145`). Cleanup rejects a replacement only when an ID was already recorded; otherwise it adopts the current status's ID and calls untargeted `game.stop` (`session.ts:149-167`). It then describes that session as owned by the test run.

A temporary diagnostic called the actual `runOwnedTestSession` with a deterministic RPC seam: initial stopped status, successful play acknowledgement, failed first post-start status, then a running `replacement-session` at cleanup. The helper issued `game.stop` despite never having acquired a session identity during the run:

```json
{"ownershipResult":{"reports":{},"timedOut":false,"error":"First post-start status failed","cleanup":{"stopAttempted":true,"stopped":true,"reason":"stopped the PIE session started by this test run","pieSessionId":"replacement-session"}},"cleanupCalls":["game.pie.status","game.play","game.pie.status","game.pie.status","game.stop"]}
```

This proves the sidecar's command policy under the supplied replacement scenario; no live Studio interruption was performed.

**Impact and mechanism**: If the user stops/restarts PIE before the test runner establishes its identity, a status failure, timeout, or cancellation can lead cleanup to stop the replacement session. The fallback makes the identity comparison vacuous precisely when ownership is unknown. A successful start acknowledgement is not evidence that whichever session appears at cleanup is the same session.
**Smallest responsible action**: Fail closed when cleanup has no established nonempty owned session ID. Do not acquire ownership during cleanup; report that ownership is unverified and leave the current session untouched. Continue stopping a positively identified session only when a fresh status matches it. Use a start-returned identity if the existing native contract supplies one, without requiring a new native ownership protocol for this fix.
**Scope and non-goals**: Limit the change to Luau-test ownership bookkeeping and cleanup reporting, with bounded cancellation-independent cleanup retained. Do not stop arbitrary current PIE to guarantee cleanup, add global Studio arbitration, redesign `game.play`, or claim to eliminate every status/stop race.
**Verification**: Add package-level regressions for a failed first status query, cancellation before identity acquisition, and startup timeout without an acquired ID. Assert no `game.stop` and no claimed ownership in each unknown-ID case. Also assert a known matching session is stopped and a known replaced session is untouched. Exercise `createLuauTestTool` restoration so the surrounding cleanup does not silently manufacture a successful ownership verdict. Run the focused Luau-test suite.
**Why now**: `2583216a` introduces the Luau test runner and promises to stop only its owned session. The unsafe fallback is in that new normal failure-cleanup path; fixing it now prevents future tests from relying on an invalid ownership guarantee.
**Delivery**: Created issue [#557](https://github.com/overdare/diligent/issues/557) — `fix(studiorpc): skip Luau cleanup when PIE ownership is unverified`.
