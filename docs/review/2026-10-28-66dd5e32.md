## Findings

### F-01 — Code-mode workers outlive their deleted or shut-down owners

**Disposition**: Act now
**Lens**: Ownership | Operational correctness
**Confidence**: High
**Evidence**: `CodeModeSession` creates real workers and retains yielded cells; its `dispose()` terminates them (`packages/runtime/src/tools/code-mode/session.ts:371-399`). A driving call removes its abort listener on yield (`session.ts:155-178`), so aborting a later runtime controller does not terminate a detached cell. `RuntimeAgent` owns the session but exposes no cleanup integration (`packages/runtime/src/agent/runtime-agent.ts:12-33`). Thread deletion calls `manager.dispose()` (`packages/runtime/src/app-server/session-handlers.ts:233-236`), whose orchestrator disposal only releases provider stream resources (`packages/runtime/src/session/turn-orchestrator.ts:80-93`). App-server shutdown waits for turns and child registries but does not dispose the code session (`packages/runtime/src/app-server/server.ts:302-318`). Child close/shutdown also lacks session disposal (`packages/runtime/src/collab/registry.ts:755-784`, `841-850`). A source search found no production caller of `CodeModeSession.dispose()`.

Two temporary diagnostics on current HEAD exercised the real runtime assembly and public RPC helpers. A synthetic provider requested `exec` with a timer-driven heartbeat loop and a 100 ms yield, then ended its response. After normal turn cleanup, one diagnostic deleted the thread through `thread/delete`; the other kept the thread loaded and called `server.shutdown()`. Both observed the same retained cell still updating its store after cleanup, with zero calls to session disposal:

```json
{"operation":"delete","disposalCalls":0,"liveCellsAfterCleanup":1,"before":"1793222188957","after":"1793222189060"}
{"operation":"shutdown","disposalCalls":0,"liveCellsAfterCleanup":1,"before":"1793222191324","after":"1793222191427"}
```

The diagnostic restored instrumentation, explicitly terminated its workers, and removed its temporary projects; its script was removed from the worktree. The synthetic provider is only a deterministic input: the evidence is continued execution by the real worker after the actual lifecycle operations.

**Impact and mechanism**: Yielded guest code continues to consume CPU, memory, timers, and output buffers after its owner becomes inaccessible. `unref()` allows process exit; it does not stop execution in a long-lived Web host. The eight-cell eviction limit is local to a code session and runs only when another cell starts in that same session, so it cannot reclaim cells abandoned by deleted/replaced owners. Repeated thread or child lifecycles can therefore accumulate orphaned workers despite successful deletion/shutdown responses. Nested tool calls are held while detached, so this finding does not claim unattended Studio or filesystem mutations.

**Smallest responsible action**: Connect code-session disposal to an explicit runtime-owned resource-release path. Invoke it when a thread/child is deleted, closed, or shut down, and when an agent/code-session owner is permanently replaced without transferring its session. Ensure app-server shutdown releases loaded root sessions as well as children. Keep ownership transfer explicit where a tool refresh intentionally reuses the existing code session.

**Scope and non-goals**: Cover root and child resource ownership, idempotent cleanup, and abandoned-agent replacement. Preserve yielded cells and `store()` across normal turns and supported in-place tool refreshes; do not dispose at every response boundary. Do not redesign code-mode execution, add a global worker registry, change permissions, introduce a new protocol, or claim that `node:vm` is a security sandbox.

**Verification**: Add a code-mode lifecycle regression that starts a yielded heartbeat cell, waits for the originating turn and cleanup to finish, then deletes the thread through public RPC. Assert the worker terminates and its heartbeat stops, not just that deletion succeeds. Independently prove app-server shutdown terminates a loaded thread's cell, and add package-level child close/shutdown and abandoned-owner replacement coverage. Assert repeated cleanup is harmless and ordinary next-turn `exec_wait`/`store()` continuity still works. Run focused code-mode, collaboration, and app-server lifecycle suites.

**Why now**: `6662cc64` introduces worker-backed code mode; `81282795` enables it by default for roots and children. The same range adds persistent Goal runs and more long-lived host/session activity. Resource cleanup must match these supported lifecycles now, before further persistent executors inherit an owner that can be discarded without releasing them.

**Delivery**: Created issue [#511](https://github.com/overdare/diligent/issues/511) — `fix(runtime): dispose code-mode workers with their owning sessions`.
